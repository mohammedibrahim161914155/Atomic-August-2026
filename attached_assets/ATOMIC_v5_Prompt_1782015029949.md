## §1 — CLAUDE-GRADE INTERFACE REDESIGN

This section is specified against an exact visual reference, not an abstraction. Build to this precision. Where a reference feature has no Atomic equivalent, the mapping is defined explicitly below — do not leave anything unmapped, and do not copy any third-party branding, wordmarks, or copy verbatim.

### 1.1 Two Distinct UI States

The chat interface has two states that must be built as genuinely separate component trees, not one component with conditional rendering bolted on:

- **Empty/Greeting State** — shown when a session has no messages yet.
- **Active Thread State** — shown once the first message is sent. The greeting, status banner, and quick-action pills are replaced by the scrolling message thread and a docked composer.

**1.2.1 — System Status Banner**

A dismissible, persistent-dismissal banner component (dismissal state survives refresh, scoped per specific notice, not shown again once dismissed). Used for things like: a configured model becoming temporarily unavailable, a new model becoming available, the Curator's official-source search degrading to cached results. Structure: leading text, "Learn more" link (opens relevant docs/settings), trailing `X` dismiss control.

**1.2.2 — Quick Action Pills**

Icon + label pills below the composer. Map to Atomic's actual structure rather than copying any reference verbatim:

| Pill | Icon concept | Action |
|---|---|---|
| Start scoping | compass/pencil | Opens a new session in Artemis mode |
| Resume blueprint | layers/cube | Jumps to the active project's pipeline view |
| Explore blueprint | search/lightbulb | Opens a new session in General mode against the current blueprint |
| Review changes | diff/check | Opens Curator mode with the latest Refinement Report |
| Atomic's pick | spark | Auto-routes to whichever mode the system determines is most relevant given project phase |

These five are a sensible default set, not a rigid requirement — but every pill must route to a real, working action. No decorative pills.

### 1.3 Composer — Exact Behavior

- Rounded, multi-line, auto-resizing text area. Placeholder text: `Type / for skills`.
- Typing `/` opens an inline skill/tool picker anchored to the cursor — this is the literal UI mechanism for the Skills System (v4.0 §5) and tool selection. Arrow-key navigable, `Escape` closes it, `Enter`/click selects.
- Bottom row, left-aligned: a `+` button (see 1.4 for its menu).
- Bottom row, right-aligned, in this exact order: model selector pill (see 1.5), microphone icon (voice input), waveform/voice-mode icon (voice conversation mode).
- When the input has content, the rightmost control becomes a solid send button (filled accent color, up-arrow icon), replacing the empty-state icon cluster's resting position.
- During streaming, the send button is replaced by a stop/interrupt control. This is not optional — the user must always be able to interrupt a generating agent from the composer itself.

### 1.4 The `+` Menu — Exact Contents

A popover anchored above the `+` button. Sectioned with dividers exactly as follows:

**Section 1 — Context attachment**
- `Add files or photos` (shortcut: `Ctrl+U` / `Cmd+U` on Mac)
- `Take a screenshot`
- `Add to project` → submenu listing the user's Atomic projects (v4.0 §2.8 Multi-Project Architecture)
- `Add from GitHub` → repo/branch picker, pulls real repo context into the session
- `Add from Blueprint` → **Atomic-native addition** — submenu to attach a specific pillar's output or a specific blueprint version directly into message context. This is the concrete implementation of "reference a pillar or version in chat."

**Section 2 — Capabilities**
- `Skills` → submenu listing available skills (v4.0 §5) with toggles for which are active this session
- `Connectors` → submenu listing connected MCP servers (§2 below) with toggles
- `Add plugins...` → opens the plugin install/manage flow (§2.3 below)

**Section 3 — Tools**
- `Web search` → toggle. When toggled on for Curator mode specifically, it must default to **official-source-restricted mode** per the system-wide trusted-sources principle (v4.0 §1) — the menu item should visually indicate when source-restriction is active (e.g., a small lock or shield glyph next to the toggle) rather than behaving as an unrestricted general web search.

Popover behavior: focus-trapped while open, closes on `Escape` or outside click, fully keyboard navigable, submenus open on hover or right-arrow.

### 1.5 Model Selector — Exact Structure

Two linked popovers, opened from the model pill in the composer.

**Primary popover (model list):**
- One row per available model: name, one-line capability descriptor, status indicator. If a model is gated/unavailable, show an `Upgrade` affordance instead of a checkmark; otherwise show a checkmark on the currently selected model.
- Divider.
- `Effort` row — shows the current effort level, chevron opens the secondary popover.
- `More models` row — chevron, expands to the full dynamically-loaded model list (never hardcoded — v4.0 §13 Model Configuration).

**Secondary popover (effort/thinking):**
- Explanatory text: effort level tradeoff (higher = more thorough, slower, more budget consumed).
- Effort levels: `Low` (marked Default), `Medium`, `High`, `Max` — single-select, checkmark on active.
- Divider.
- `Thinking` toggle — enables extended reasoning for complex tasks, with its own one-line description.

**Engineering mapping:** this entire UI is the front-end for `PillarSubAgent.config.model` and the equivalent Artemis/Curator model config blocks from v4.0. Extend `ModelConfig` to include:

```typescript
interface ModelConfig {
  modelId: string
  effort: 'low' | 'medium' | 'high' | 'max'
  thinkingEnabled: boolean
}
```

This selector must be available per-agent (Artemis/Curator/General) and, per v4.0 §13, optionally per-pillar for power users.

### 1.8 Design Tokens, Accessibility & Responsive Behavior

**Design tokens:** single coherent token system — dark-first color palette with a distinct accent per chat mode (consistent with v4.0 §8's visual identity requirement), serif display font for greetings/headers, sans-serif for UI chrome, monospace for code and structured data.

**Accessibility:** full keyboard navigation across composer, menus, and settings. `aria-live` regions for streaming content. Color contrast meets WCAG AA minimum throughout. Focus management on every popover/modal open and close.

**Responsive behavior:**
- On mobile, the sidebar collapses into a slide-in drawer (1.6).
- On mobile, the `+` menu and the model selector open as bottom sheets rather than floating popovers.
- On mobile, the composer becomes a full-width docked bottom bar.
- On mobile, the Workspace Panel (1.10) becomes a swipeable secondary screen rather than a side-by-side pane.
- Tablet breakpoints use the desktop popover pattern but a collapsed-by-default sidebar.

### 1.9 Active Thread State

Once the first message is sent, the empty state is replaced entirely. This state was underspecified against the visual reference (which only showed the empty state) and must be built to the following standard, carried over from the core chat requirements:

**Message rendering:**
- Streamed markdown with incremental parsing — no flash of unformatted content as tokens arrive.
- Code blocks: syntax-highlighted, language-labeled, with a copy action and, in Curator mode, an "Apply to workspace" action for proposed code-level edits.
- Collapsible tool-call and reasoning trace blocks — every tool call an agent makes must remain inspectable, never hidden by default in a way the user can't recover.
- Inline citation chips for the Curator's sourced claims: hovering shows source name and retrieval date; clicking opens the source. This is the UI expression of v4.0 §10's citation requirement.

**Message actions:**
- Copy, regenerate, edit-and-resubmit for user messages, and a feedback hook (thumbs up/down).
- Contextual suggested follow-ups after agent responses — e.g. after Artemis completes a brief: "Start the pipeline" / "Revise tech stack."

**Loading states:**
- A skeleton/typing indicator while the first token of a response is in flight.
- If a response stalls (no token received within a defined timeout), surface a visible "still working" state rather than leaving the user looking at a frozen UI — this ties directly to the no-frozen-UI requirement in v4.0's Delivery Standard.

### 1.10 Workspace Panel

This is the concrete UI surface for the "Spaces" concept defined in v4.0 §4 — every agent's dedicated, persistent output zone, made visible and navigable.

- A toggleable right-hand panel, opened from the top bar or directly via the sidebar's `Workspaces` item.
- Content-typed tabs matching the active agent: Brief / Breakdown for Artemis, Blueprint / Pillars for the pipeline, Report / Diffs for the Curator.
- Live token-by-token rendering as content streams in — the literal UI expression of v4.0 §13's Live Workspace Output requirement.
- A version selector in the panel header with an inline diff toggle, directly wired to the Version History data model from v4.0 §12.
- Export/download actions for the current workspace's content.
- Reachable independent of an active chat session — a user can open a project's Workspaces directly from the sidebar without starting a new conversation first.

## §2 — SDK, MCP & PLUGIN ARCHITECTURE (MULTI-CLIENT)

The SDK, MCP server, and plugin system already exist in scaffolded form. This section's job is to **finish** them to the point where Atomic can be installed as a working integration inside third-party AI coding assistants and agent platforms — not just consumed from within the Atomic app itself.

**Target clients for installability:** Cursor, Codex, Claude Code, OpenCode, Kilo Code, Claude.ai/Claude Desktop, Manus, and any other tool that supports MCP server installation or a comparable plugin/connector mechanism.

> **Verification requirement:** config file formats and capability support differ across these clients and change over time. Before building each client adapter, verify the *current* official configuration schema and supported MCP capabilities directly from that client's official documentation. Do not rely on assumed or memorized formats — this is the same official-sources discipline already required of the Curator (v4.0 §1), applied to your own build process.

### 2.1 Canonical Manifest — Single Source of Truth

```typescript
interface AtomicConnectManifest {
  id: string                          // 'atomic-mcp'
  version: string                     // semver
  name: string
  description: string

  transports: {
    stdio: boolean
    sse: boolean
    streamableHttp: boolean
  }

  capabilities: {
    tools: ToolDefinition[]
    resources?: ResourceDefinition[]
    prompts?: PromptDefinition[]
    sampling?: boolean
  }

  auth: {
    type: 'none' | 'apiKey' | 'oauth'
    scopes?: string[]
  }

  minimumProtocolVersion: string
}
```

Every per-client config file is **generated from this manifest**, never hand-maintained separately. If the manifest changes, regenerating client configs is a build step, not a manual editing task across five different files.

### 2.2 MCP Server — Production Standard

- Implement both `stdio` and remote (`SSE`/`streamableHttp`) transports — different clients prefer different transports; the server must support both so it isn't locked out of any target.
- **Capability negotiation:** on connection, detect which MCP primitives the connecting client actually supports (tools-only vs. tools+resources+prompts+sampling) and respond within that client's supported feature set rather than assuming full parity. Log the negotiated capability set via the Observability Layer (v4.0 §2.2).
- Expose Atomic's core actions as MCP tools bound to the existing `ToolConfig` system (v4.0 §6) — no parallel, redundant tool-definition system.
- Every MCP tool call is bound by the same workspace permission model as in-app agents (v4.0 §2.7). A connecting external client cannot write to a workspace its calling context isn't authorized for — there is no separate, looser enforcement path for external callers.
- **Per-client config adapters:** a generator that produces the correct config file (or equivalent installation artifact) for each target client, from the canonical manifest. Each adapter must be verified against that client's current official docs and covered by its own test.
- **Unified installer CLI:** a single command (e.g. `npx atomic-connect install`) that detects which supported clients are present on the machine and offers to configure each one automatically, writing the correct adapter output to the correct location for that client.
- **Credential storage:** an OS-credential-store abstraction (`CredentialStore` interface) so API keys/tokens are never written to plaintext config files where avoidable, and are stored consistently regardless of which host client triggered the install.
- **Conformance test suite:** automated tests verifying MCP protocol compliance independent of any specific client, plus smoke tests against each real target client where headless/scripted invocation is feasible.

### 2.3 Plugin System — Production Standard

This is Atomic's *internal* extensibility mechanism (custom Skills, custom pillar sub-agents, custom validation gates, custom workspace panel renderers) — distinct from MCP, which is the cross-tool interoperability layer.

```typescript
interface PluginManifest {
  id: string
  name: string
  version: string
  permissionsRequested: (WorkspacePermission | ToolPermission)[]
  entryPoint: string
  compatibleAgents: AgentType[]
  author: string
}
```

- Supported plugin types: custom Skills, custom pillar sub-agents, custom validation gates, custom workspace panel renderers.
- Sandboxing: a plugin cannot request or receive permissions beyond what its manifest declares. The workspace write layer rejects any plugin call outside its granted scope — same enforcement point as the rest of the security model.
- Lifecycle: install → user reviews and approves requested permissions → enable → disable/uninstall at any time.
- **Re-approval on permission change:** any plugin update that requests new permissions beyond its previously approved set must block until the user explicitly re-approves — never silently escalate.
- A hosted plugin marketplace is out of scope for this phase, but the `PluginManifest` and versioning model must already support one without requiring rework later — confirm this by checking the manifest alone contains everything a listing page would need (name, description, version, permissions, author, compatible agents).

### 2.4 SDK — Production Standard

```typescript
interface AtomicClient {
  sessions: SessionAPI
  pipeline: PipelineAPI
  blueprint: BlueprintAPI
  events: EventSubscriptionAPI
  workspaces: WorkspaceReadAPI    // read-only outside the app process
}
```

- Authentication via scoped tokens — never embedded client-side in plaintext.
- A typed error model (`AtomicAuthError`, `AtomicRateLimitError`, `AtomicValidationError`, etc.) — no generic string throws.
- API reference documentation auto-generated from source comments as part of the build pipeline, not maintained by hand — docs and code must be the same artifact, never hand-synced.
- Published as a properly semver'd package with a maintained changelog; breaking changes require a major version bump, never a silent patch-level break.
- Full test coverage including failure-path tests: revoked permissions, malformed manifests, unreachable MCP servers, expired tokens. Built on the same `MockLLMClient`-style mocking pattern used by the core app (v4.0 §2.10).

### 2.5 Documentation Deliverables

One canonical reference document plus a per-client quickstart guide for each of the seven target clients listed above, each verified against that client's current official install/config flow at the time of writing.

### 2.6 External Call Governance

Every call into Atomic from an external client — Cursor, Claude Code, or any other connected tool — routes through the **same** `TokenBudgetManager` and `RateLimitManager` as internal agent calls (v4.0 §2.4). There is no separate, unmetered path for external traffic. Per-client budget caps are configurable in `Settings → Connectors`, with the ability to set a hard ceiling per connected client so a misbehaving or overly aggressive external integration cannot exhaust a session's or project's budget unnoticed.

### 2.7 Protocol & Client Compatibility Matrix

Maintain a living compatibility table — committed alongside the docs, not just known informally — tracking, per target client: supported transport(s), supported MCP capabilities (tools/resources/prompts/sampling), and the last-verified protocol version. This table is re-verified and updated on every manifest version bump, not left to go stale.

### 2.8 Manifest Versioning & Migration

When the canonical manifest changes version, already-installed client configs must not be silently left stale. The installer CLI provides an upgrade path:

```
atomic-connect upgrade [--target <client>]
```

This detects previously-installed client configs, re-runs the relevant adapter against the new manifest, and reports what changed. Manifest version bumps that remove or change capabilities must be flagged clearly to the user before the upgrade is applied, with a path to review the diff.

### 2.9 Opt-In Telemetry

Anonymous, **opt-in only**, usage analytics for external installs — which client connected, which tools were invoked, success/failure rates, and latency. Explicitly disclosed, off by default, and revocable at any time from Settings. This telemetry must never include blueprint content, project data, conversation content, or anything that could identify what the user is building — only operational metadata about the integration itself.

### 2.10 Uninstall Flow

```
atomic-connect uninstall [--target <client>]
```

Cleanly removes only the config entries Atomic's installer originally added, without touching unrelated configuration in that client's file, and revokes/cleans any credentials stored via the `CredentialStore` abstraction. An uninstall must never leave orphaned, unrevoked tokens behind.

### 2.11 Sandbox / Dry-Run Mode

An install/test mode (`atomic-connect install --sandbox`) that connects a new client integration against a disposable demo project rather than the user's real project data. This lets a user — or the build/test process — verify a new client integration works correctly before trusting it with real blueprints and workspace content.

## §3 — ENGINEERING & RELEASE STANDARDS

Apply these across the entire codebase, not just the features introduced in this document.

**CI/CD Gates — all required before merge, no bypassing:**
- Typecheck (`tsc --noEmit` or equivalent, zero errors)
- Lint (zero warnings treated as failures, not just zero errors)
- Unit tests, integration tests, contract tests for the sub-agent interface (v4.0 §2.10)
- Build verification
- Dependency vulnerability scan (run on every PR and on a recurring schedule)
- Bundle size / performance budget check — build fails if exceeded without an explicit, justified override
- **Accessibility gate:** automated a11y checks (e.g. axe-core or equivalent) run in CI; failures block merge the same as any other gate — this enforces what §1.8 specifies rather than leaving it aspirational

**Dependency & Supply Chain Security:**
- Lockfile committed and enforced; no wildcard version ranges for production dependencies
- Automated vulnerability scanning with a defined response SLA for critical findings

**Release Discipline:**
- Semantic versioning enforced via automated changeset/changelog tooling — no manual version bumps
- Any large or risky feature ships behind a feature flag, default off, with a defined rollout plan
- **Rollback strategy:** every feature flag has a defined kill-switch procedure; deploys must be revertible without data loss

**Reliability & Scale:**
- Define error budgets/SLOs for core flows — pipeline completion rate, agent response P95 latency, workspace write success rate — and instrument the Observability Layer (v4.0 §2.2) to track actual performance against them
- **Load/concurrency testing:** the orchestrator's parallel pillar execution path gets dedicated load tests simulating maximum configured parallelism, verifying no race conditions in workspace writes or event bus delivery under load
- Any production-path failure discovered during build or test gets a brief written root-cause note committed alongside the fix, not just a silent patch

**Architecture Decision Records (ADRs):**
- Any non-trivial architectural choice — including decisions made while implementing this document, such as the removal of Fusion Models from scope — gets a short committed ADR: context, decision, consequences. This preserves the reasoning for whoever (human or AI) touches the system next, not just the resulting code.

**Data Handling & Retention:**
- A documented policy for how long conversation history, blueprints, and workspace content are retained, and how deletion requests are honored.
- Project data is never used to train or fine-tune models without explicit, separate, opt-in consent — this is distinct from and in addition to the telemetry opt-in in §2.9.

**Secrets Management:**
- No secrets in source control; `.env.example` committed, never `.env`
- Credentials for MCP/connector auth stored encrypted at rest via the `CredentialStore` abstraction (§2.2)

**Review Discipline:**
- A defined PR/change checklist (what changed, why, how it was tested, screenshots for UI changes) — applied even when the "author" is the coding agent itself; self-review against this checklist before declaring any task complete

## §4 — UNIFIED DELIVERY STANDARD (v4.0 + v5.0 REVISED)

- Phase 0's completion audit gates all new work — nothing here gets built on an incomplete v4.0 foundation.
- The interface must match §1's specification precisely — composer behavior, `+` menu contents, model/effort selector, sidebar, settings pattern, active thread rendering, and workspace panel are not open to reinterpretation.
- The MCP server must be genuinely installable and functional in at least Cursor, Claude Code, and one of Codex/OpenCode/Kilo Code as a verification bar — not merely theoretically compatible.
- External calls are governed by the same budget and rate-limit infrastructure as internal calls — no unmetered side door.
- The SDK, MCP client, and plugin runtime meet the same standard as the core app: typed, tested, documented, and security-reviewed.
- Every CI/CD gate in §3 is enforced, not aspirational — a passing pipeline is required before any feature in this document is considered shippable.
- Every feature across v4.0 and v5.0 Revised must be demonstrably functional end to end before being considered done. No stubs, no `// TODO`, no placeholder logic, no `any` without justification.
- Code must pass review by a senior engineer at a FAANG-level company without embarrassment.

## §5 — MASTER DEFINITION OF DONE

**Infrastructure**
- [ ] Event Bus, Observability Layer, LLM Abstraction, Token/Rate Manager, Prompt Registry, Validation Gates, Security Model, Multi-Project Architecture, Context Window Management all built and unit-tested
- [ ] No component bypasses the Event Bus for inter-component communication
- [ ] No agent calls an LLM provider SDK directly — all routed through `LLMClient`

**Agents & Orchestration**
- [ ] Every pillar conforms to the `PillarSubAgent` contract — none bypass it
- [ ] Artemis, the Curator, and General Mode each respect their workspace permission boundaries, enforced at the data layer
- [ ] Only the Curator can write to `pipeline_workspace`
- [ ] Blueprint versioning creates a new version on every edit; no destructive overwrites; V1 is permanently preserved

**Interface**
- [ ] Empty state and Active Thread state are built as separate component trees and both fully functional
- [ ] Composer, `+` menu, and model/effort selector match §1.3–1.5 exactly
- [ ] Workspace Panel streams live content and is reachable independent of an active chat session
- [ ] Settings follows the identical left-rail/right-pane pattern across every section
- [ ] Full keyboard navigation, `aria-live` streaming regions, WCAG AA contrast verified
- [ ] Responsive behavior verified on mobile and tablet breakpoints

**SDK / MCP / Plugins**
- [ ] MCP server verified working in at least three target clients, including Cursor and Claude Code
